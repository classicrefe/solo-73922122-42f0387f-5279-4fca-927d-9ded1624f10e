# 货运数仓:来源核对与运单回补

货运数仓收到两份没标版本的导出 CSV(运单表导出、签收表导出),第一项功能是用
一份 JSON 证据包(两表起点快照 + 起止提交号 + 逐事务行变更前后值)重放提交
历史,判断两份 CSV 是否可能来自同一次提交。

第二项功能是**运单回补**:下游库有几票导入出错,按获批单号把下游两份 CSV 中
这些运单(及其名下签收明细)整体换成目标提交完成后的版本,输出两份 CSV 打成
的 ZIP;范围不足或证据无效时说明原因、不出包。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

页面顶部有两个页签:

- **来源核对**:上传运单导出 CSV、签收导出 CSV、证据包 JSON。
  页面底部可直接下载样例三件套试跑(预期交集:提交 100、102、106、108、110)。
- **运单回补**:上传下游运单 CSV、下游签收 CSV、证据包 JSON,填写目标提交号和
  获准回补的单号。页内附样例三件套与建议参数(目标提交 505,获准 `WB100, WB101`)。

服务健康检查:`GET /api/health`(Compose 已配置 healthcheck)。

本地自测(不需要 Docker):

```bash
pip install -r requirements.txt   # HTTP 接口测试另需 httpx2
python3 -m tests.selftest
```

## 输入格式

### 运单导出 CSV

只含已签收运单,列:`单号,状态,件数`(UTF-8,键 `单号` 不可重复)。

### 签收导出 CSV

只含已签收运单的签收明细,列:`签收号,单号,实收件数`(键 `签收号` 不可重复)。

### 证据包 JSON

```json
{
  "start_commit": 100,
  "end_commit": 110,
  "snapshots": {
    "waybills": [{"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"}],
    "receipts": [{"签收号": "RC0001", "单号": "WB0001", "实收件数": 3, "签收人": "张三"}]
  },
  "transactions": [
    {"commit": 101, "changes": [
      {"table": "waybills", "op": "update", "key": "WB0001",
       "before": {"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"},
       "after":  {"单号": "WB0001", "状态": "已签收", "件数": 4, "目的地": "上海"}}
    ]}
  ]
}
```

- 表名支持 `waybills`/`运单表`、`receipts`/`签收表`;`op` 为 `insert`/`update`/`delete`
  (insert 的 `before` 为 null,delete 的 `after` 为 null)。
- 快照行可含任意额外列,导出比对只取规定字段;但变更 `before` 必须与重放出的
  整行完全一致(含额外列),否则视为前值对不上。
- 数值比较按字符串归一化:JSON 数字 `3` 与 CSV 文本 `"3"` 视为相等。

## 来源核对判定规则

- 导出视图:运单导出 = 状态为「已签收」的运单,取(单号, 状态, 件数);
  签收导出 = 单号属于已签收运单的签收行,取(签收号, 单号, 实收件数)。
- 只在**起点**(起始提交号)和**每笔事务整体应用之后**与 CSV 比对;
  键集合与对应值完全一致(按编号和值)记为一个吻合提交。
- 输出:各文件完全吻合的提交区间、两者的交集;交集为空时提示
  「所查范围内没有共同来源」。
- 下列情况提示「证据不足」并停止核查:
  - 日志缺号:提交号不连续、尾部缺失或超出终止提交号;
  - 变更前值与重放状态对不上(含 insert 前键已存在、update/delete 前键不存在);
  - 起点快照键重复或缺键列。
- 变更条数上限 50000 条,超出直接拒绝。

## 运单回补规则

输入:下游运单 CSV、下游签收 CSV(列与上面完全相同)、证据包 JSON、目标提交号、
获准单号(逗号/顿号/空格/换行分隔均可)。

1. **整份证据先校验**:从起点快照重放完整日志(连续性、前后值、键一致性都按
   来源核对的同一套规则);任何一处不成立即判定证据不足,不出包。
2. **取目标版本**:取目标提交完成后的两表导出视图。目标提交可以是区间内任一
   提交,也可以是起点(`start_commit`,即起点快照本身)。导出列沿用现有导出:
   运单 `单号,状态,件数`,签收 `签收号,单号,实收件数`。
3. **一票整体替换**:每票运单 = 运单行 + 该单号名下(旧版或目标版)的全部签收
   明细。范围内的整票换成目标版;目标版已不存在的行删除。
4. **改挂闭包**:若同一签收号在旧版与目标版挂到不同运单,则新旧两票必须一起
   回补;由此连带卷入的运单继续展开,直到不动点。获准范围必须覆盖整个闭包。
5. **范围不足**:不出包,列出**最少还需补选的运单号**,以及每个单号涉及的签收号
   (含该签收号在原版/目标版分别挂在哪个运单)。
6. **范围外保留原值**:范围外的运单行和签收行一律照抄下游 CSV 的旧值,不引入
   目标版本里新增的范围外数据。
7. **出包前完整性校验**:回补后的每条签收明细都必须能对应到一条运单行;有落单
   签收则不出包并逐条列出。
8. 以上全部通过,才提供 ZIP(`waybills.csv` + `receipts.csv`,UTF-8 BOM + CRLF)。
   其余情况一律返回原因,不提供下载。

获准单号若在两版导出里都没有任何行(可能已回补过),不产生变更,页面上会单独
提示;完全未知的单号按输入错误拒绝。

### 回补样例

`app/backfill_sample.py` 构造了提交 500..505 的场景:下游 CSV 停在起点 500;
目标提交 505 里 WB101 及 RC1001 已删除、RC1002 由 WB101 改挂到 WB100、WB102
退出导出。只获准 `WB100` 会提示还需补选 `WB101`(涉及签收号 `RC1002`);获准
`WB100, WB101` 后出包,范围外的 WB102/WB106 保留原值。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 操作页(来源核对 / 运单回补两个页签) |
| GET | `/api/health` | 健康检查 |
| POST | `/api/verify` | 来源核对 |
| POST | `/api/backfill` | 回补校验与出包 |
| GET | `/api/sample/{waybills.csv,receipts.csv,evidence.json}` | 来源核对样例 |
| GET | `/api/backfill/sample/{waybills.csv,receipts.csv,evidence.json}` | 回补样例 |

`POST /api/backfill` 表单字段:`waybill_csv`、`receipt_csv`、`evidence`(文件)、
`target_commit`、`approved`。返回:

- `200` `status=ok`:含 `package`(`filename`、`files`、`size_bytes`、
  `content_base64`)、`stats`(两份文件的新增/删除/改值清单)、`scope`、`evidence`。
- `409` `status=insufficient_scope`:含 `scope.missing`(最少补选单号)与
  `scope.uncovered`(每个单号涉及的签收号及原/目标运单)。
- `409` `status=cannot_produce`:含 `violations`(回补后无运单的签收明细)。
- `200` `status=insufficient_evidence`:证据不足及原因。
- `400` `status=invalid_input`:CSV/JSON/参数有误。

## 性能设计

不为每次提交复制整表。重放时维护:

- 两张表的当前行(按主键的字典);
- 已签收单号集合、单号 → 签收号索引;
- 两个「当前导出视图 vs 目标 CSV」的差异计数器。

每条变更只触碰受影响的键:运单变更 O(1) 更新运单侧计数,签收状态翻转时只扫描
该单号名下的签收行;签收变更 O(1)。整体复杂度 O(快照行数 + 变更条数),
5 万条变更在本机自测约 2 秒内完成(见 `tests/selftest.py`)。回补在目标点另存
一份完整表状态,闭包计算为 O(相关票的签收行数)。

## 自测覆盖

`python3 -m tests.selftest`:

1. 样例场景端到端区间/交集断言;
2. 每个提交后增量计数与全量重算一致(验证不复制整表的增量逻辑正确);
3. 交集为空 → 无共同来源;
4. 日志缺号(中间/尾部)、前值对不上、提交号超出终止号 → 证据不足;
5. 签收行改挂单号、运单状态翻转带多签收行的边界场景;
6. CSV 缺列/重复键校验;
7. 5 万条变更性能与正确性;
8. HTTP 接口(上传样例、缺号证据、坏 CSV、操作页、样例下载);
9. 回补:样例闭包/目标版整票替换/ZIP 两份 CSV 与表头、范围不足补选清单、
   起点快照作目标、目标版新增运单、多跳改挂闭包、范围外保旧值、
   落单签收拒绝出包、证据不足/越界/未知单号、空下游导出;
10. 回补 HTTP:成功出包、409 范围不足、400 参数/证据错误、页面入口、样例下载。

## 已知限制

- 「已签收」状态值固定为 `已签收`(app/core.py 中 `SIGNED_STATUS`)。
- CSV 只校验必需列,额外列不参与比对;回补输出也只写现有导出列。
- 证据包整体读入内存解析,未做流式 JSON;5 万条变更规模下足够。
- 行键(单号/签收号)在变更中不可改:after 行的键必须与记录键一致。
- 回补 ZIP 经 JSON(base64)返回并由浏览器端生成下载,超大导出(数十万行)
  需改为流式下载;当前 5 万条变更规模足够。
- 证据包只覆盖 `start_commit..end_commit`,目标提交必须落在这个区间。
